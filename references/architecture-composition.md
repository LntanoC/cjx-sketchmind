# 系统架构图构图指南

## 先建立结构模型

先识别目标系统和读者要解决的问题，例如系统边界、逻辑组件、部署拓扑或某个功能怎样运作。按目标系统的代码入口、模块声明、配置和文档确认实际主体、职责、边界、方向及协议。风格参考用于提取分层、卡片、图标和线条等画法。用户明确将参考图用作目标系统资料时，核对图中信息与适用范围。缺少的信息标为未知或说明假设，示例场景明确标注。

## 构图

- 默认先放边界和层次，再在同一层横向并列组件，最后连接真实依赖。层次依据系统实际情况选择，不强制出现客户端、网关、服务或数据层。
- 用包围区域标出已知部署、网络、信任或系统边界并写明含义；背景分层本身不代表部署或信任边界。外部系统放在适当边界之外。
- 从真实调用方或触发源开始，必要时呈现用户、外部系统、消息或定时任务。每条线按证据标方向和短动作，如「提交订单」「查询库存」「返回状态」。编译依赖、运行调用、异步消息和响应使用可区分的线型或颜色；出现多种含义时配简短图例。
- 组件卡片用「线性图标＋实际名称＋一句职责」。优先给关键主体加图标，同类主体沿用相同轮廓，例如人员、浏览器、服务、数据库、文档、CLI、Agent。使用柔和语义配色与留白，分区标题靠边，给跨层连线留足通道。图标要能单独选中或随卡片移动，避免品牌标识、表情和整图位图。
- 面向产品或跨职能读者，优先选一个有依据的典型场景。在右侧或下方按顺序写出「触发方与输入 → 关键处理与交接 → 可见结果」，沿用架构中的主体名称。编号放在场景区，使用布局关联两区。若场景有分支，标明展示的是哪条路径；详细条件、重试和异常按需拆为独立流程或时序。
- 模块较多时先展示与理解目标有关的结构，再按需拆出部署、数据或调用细节。简单结构或用户只要求概览时，保留一张架构图即可。

## 生成与检查

`templates/architecture.mmd` 是虚构示例：客户端、网关、并列服务、数据层，用于构图起点，不是任何用户项目的事实。先按实际模型重写。Mermaid 的 `flowchart` 是绘制语法，不决定图的语义；关键是节点、布局和连线表达架构关系。避免用隐形连线强排同层节点：转换器可能把它当布局约束，导致同层节点错位。

简单结构可用本地 `build`。需要图标、明确边界或并排场景时，可直接编排原生 Excalidraw 图元，也可在 Mermaid 转换后的原生画布中调整。通过 `scripts/architecture-icons.mjs` 复用原生图标，`x/y` 为图标左上角，`size` 为图标占用的正方形边长，已有组件组时传入 `groupId`。

```js
import { createArchitectureIcon } from './scripts/architecture-icons.mjs';
elements.push(...createArchitectureIcon('terminal', { x: 40, y: 64, size: 28, strokeColor: '#315EA1', groupId: 'cli-card' }));
```

按组件实际职责查阅 [架构图标索引](architecture-icon-catalog.md)，可按人员与渠道、网络、部署、数据、安全、运维、AI 或业务流程查找图标键。在本地生成脚本中导入时，用技能文件的实际路径。

把排版后的 `.excalidraw` 作为编辑源，按 [本地执行说明](excalidraw-local.md) 用 `render` 生成 PNG。打开预览，确认图标与名称一一对应、层与边界易读、箭头和标签避开卡片及标题，并检查是否能沿场景找到触发方、关键交接与结果。
